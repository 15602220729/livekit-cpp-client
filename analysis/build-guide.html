2.2 setup-linux-toolchain.sh 的选择逻辑（必须 source）

build.sh:45-50 在 Linux 上执行 source scripts/setup-linux-toolchain.sh。脚本 :17-21 会拒绝被直接执行（因为要 export 变量到当前 shell）。选择顺序（:90-140）：

  1. LLVM_ROOT 显式指定 → ${LLVM_ROOT}/bin/clang{,++}
  2. 否则 CC / CXX 都设了 → 用它们（只设一个会报错）
  3. 否则扫 /opt/llvm-*（按版本倒序）
  4. 否则从 clang-40 递减找到 clang-21
  5. 最后试裸 clang / clang++

每个候选都要通过三重校验（:66-88）：clang major ≥ 21、CC/CXX 版本一致、能找到 libclang.so（排除 *-cpp.*）。全部失败则报错：

ERROR: Linux builds require clang/clang++ 21+ and libclang.
Ubuntu 22.04 and 24.04 distro clang versions are too old.
Install clang-21 from apt.llvm.org or set LLVM_ROOT to a compatible LLVM installation.

成功时打印 CC= / CXX= / LIBCLANG_PATH=（:136-139）。

2.3 为什么不能用 GCC / 系统自带的旧 clang

ABI 陷阱：webrtc-sys/build.rs:531-547 —— 预编译 libwebrtc.a 用 Chromium 的 hermetic libc++（与系统隔离的 C++ 标准库），其 trivial_abi 标注会改变调用约定（ABI，二进制层面传参/返回值的规则）。GCC 会接受却静默忽略该属性，导致 libwebrtc.a 把 std::unique_ptr 放在寄存器返回、而 GCC 调用方去 sret 槽读，第一次使用就是野指针。因此 Linux 强制 clang++，且 build.rs:546 直接 builder.compiler("clang++")。Ubuntu 22.04 自带 clang 14、24.04 自带 clang 18，都不够。

2.5 一个容易误判的点：protoc 不用装

不是问题：cmake/protobuf.cmake:110-207 —— Linux/macOS 走 vendored 路径，FetchContent 下载并编译 protobuf 25.3，自己产出 protobuf::protoc，再由 cmake/run_cargo.cmake:41 把 PROTOC 环境变量传给 cargo。所以系统 protoc 缺失无需处理 —— 但 FetchContent 必须从 GitHub 下到那两个 tarball。只有 -DLIVEKIT_USE_SYSTEM_PROTOBUF=ON 或 Windows/vcpkg 路径才用系统 protoc。

版本由 gitlink（子模块指针，git 里 160000 commit 类型，只存 SHA）决定，不是分支或 tag。git submodule update --init --recursive 默认 checkout 到该 SHA（detached HEAD，HEAD 直接指向某个 commit 而不挂分支名）；绝不能加 --remote，否则会拉远端最新并改写 pin。rust-release-check.yml 还会校验 pinned commit 对应已发布 release。

3.3 本次拉取 client-sdk-rust 失败的完整复盘

轮次命令结果

5 条经验：
  1. 全量 clone 大仓库中断不能续传 → 用 --filter=blob:none（部分克隆，只拉 commit/tree、blob 按需），中断后已下载对象保留。
  2. 不要加 --depth 1：pin 不是分支顶端，浅克隆可能取不到该 commit。
  3. http.version=HTTP/1.1 规避 HTTP/2 CANCEL；lowSpeedLimit=0 禁用低速断连。
  4. googlesource 在本网络完全不通，只能走 GitHub 镜像；git 按 SHA 自校验，能 checkout 到 91727608 就说明内容与原仓库一致（对象哈希由内容决定）。
  5. 最终验收：三层 SHA 全部精确匹配、父仓库与子模块仓库 git status 干净、无持久化 url.* 配置、两个嵌套仓库 remote.origin.url 仍是官方地址 —— 零副作用。

3.4 cpp-tools 为空到底要不要紧

CI / 编译

builds.yml:56-60 会递归拉它，但 build.sh 与 CMakeLists.txt 完全没有引用 cpp-tools / clang-format / clang-tidy（实测 Grep 无匹配）。→ 编译不需要它的内容。

但要拉得到

submodules: recursive 若任一子模块 clone 失败，checkout 这一步会失败、整个 job 挂掉。准确说法是"不依赖内容，但依赖能拉到"。

本地 lint

AGENTS.md 要求根级 .clang-format / .clang-tidy 符号链接，需 git submodule update --init cpp-tools + ./cpp-tools/install.sh。本机为空 → lint 现在跑不了，但不影响编 so。

lint 不是编译前置

ci.yml:114-118 与 :139-143 的 builds / cpp-tools 都只 needs: changes，并行独立，lint 失败不阻止 build 开始。

5.1 命令与 preset 映射

CMakePresets.json 结构：隐藏基础 sdk-defaults（LIVEKIT_CAPTURE=""）、tests、vcpkg（仅 Windows）、linux-base / macos-base（Ninja、LIVEKIT_USE_VCPKG=OFF、CMAKE_EXPORT_COMPILE_COMMANDS=ON），再派生 24 个 configure preset。常用选项（build.sh:71-85）：--capture[=list] / --no-capture、--bundle --prefix、--archive、--version、-G、--macos-arch。

5.2 configure / build / install 的细节

  • 编译器一致性检查（build.sh:214-233）：若 build-release/CMakeCache.txt 缓存的 CMAKE_CXX_COMPILER 与本次选中的不一致，直接报错 Run './build.sh clean' and retry。换 clang 版本后必须先 clean。
  • configure（:235-255）：cmake --preset <PRESET> -DLIVEKIT_CAPTURE=...；preset 失败会回退传统 cmake -S . -B；成功后把 compile_commands.json 符号链接到仓库根。
  • 并行度（:263-297）：优先 CMAKE_BUILD_PARALLEL_LEVEL，否则取逻辑 CPU 数，兜底 2。
  • bundle（:299-357）：cmake --install --prefix <PREFIX>，默认 ./sdk-out/livekit-sdk；检查 lib/cmake/LiveKit/ 下三个 config 文件是否齐全。
  • 构建元数据：generated/include/livekit/build.h 生成在构建目录，不写回源码树（AGENTS.md 要求）。

run_cargo.cmake 还负责 PROTOC（:41）、CARGO_TARGET_DIR（:43-45）、RUSTFLAGS / LD_LIBRARY_PATH（:47-50）。Linux 上 RUST_TARGET_TRIPLE 为空（CMakeLists.txt:264-272 只在 macOS 赋值），所以不加 --target —— 原生编译。

硬约束：client-sdk-rust 是混合仓库；.cpp 归 C++ 编译器、.rs 归 rustc，由 build.rs（构建脚本，正式编译前先编译并运行的一段 Rust 程序）统一调度。新增 .cpp 必须登记进 build.rs:67-102 的 builder.files(...)，否则根本不参与编译。

5.4 feature hash 与两个 bundle

CMakeLists.txt:274-290：按 LIVEKIT_CAPTURE 生成的 cargo feature 组合算 SHA256 前 16 位，把 Cargo 输出隔离到 client-sdk-rust/target/cpp-<hash>/（可用 CARGO_TARGET_DIR 改根）。standard（capture=none）与 capture（capture=all）互不共享 Rust 产物，要各编一次 Rust —— 这正是 CI builds.yml:162-228 分两轮构建的原因。

5.5 capture 开关

--capture[=gstreamer,pattern,clock] / --no-capture（build.sh:100-212）→ -DLIVEKIT_CAPTURE= → cargo features（CMakeLists.txt:214）。GStreamer 只在包含 gstreamer 源时才需要（docs/building.md:167-211）；本机未安装，因此标准构建（--no-capture）不受影响。
