0结论速览

一句话结论 能改，但不是加个开关；而且必须先分清你要的是"让 SDK 内部用硬解"还是"把压缩码流本身拿出来"。
不能只改 C++ SDK 或给现有 VideoStream 加参数实现 —— 接收端 sink 的类型决定了拿到的必然是解码后的像素帧。
现状（不改）

下行只输出解码后的像素帧（I420 / NV12 / RGBA）。

拿不到码流 默认软解

方案 A · 硬解替换

实现 webrtc::VideoDecoder 并注册进工厂，让 WebRTC 内部改用你的硬件解码器。

不动 FFI 协议 不动公开 API

方案 B · 旁路码流

在接收侧 FrameTransformer 链上旁路复制 GetData()，把压缩访问单元导出给应用。

跨 4 层 fork 级改动

诉求定义可行性改动量
ASDK 内部 WebRTC 解码器换成硬解；C++ 仍拿像素帧可行，已有同类先例集中 webrtc-sys
B压缩码流旁路导出给应用 / 外部 VPU可行，已有可照抄通道跨 4 层新增 API
针对"嵌入式硬件解码"的推荐 以 A 为主；只有当码流必须落到自己的解码器 / 录制 / 转发时才上 B（或 A+B）。详见 第 5 章。

2需求拆解与判别

目标"让嵌入式设备进行硬件解码"，其实对应两种不同系统形态：

方案 A方案 B
谁调用硬件解码器WebRTC 内部（你提供 VideoDecoder 实现）你的应用 / 独立进程 / 外部 VPU
码流是否出 SDK否是
C++ 侧最终产物解码后的像素帧压缩访问单元（H264 / H265 / VP8 / AV1…）
典型场景只想省 CPU、画面照常渲染码流要录制、转发、喂给自有解码管线、多路分发
必须先回答的问题 硬件解码器是否接受"WebRTC 回调式输入"？
接受（能封装成 webrtc::VideoDecoder）→ A 足够；不接受（只吃裸流队列、或解码器在另一个进程 / 芯片）→ 必须 B。

两条路都绕不开的共同约束

  • codec 协商：嵌入式硬解通常只吃 H264 / H265，而 SFU（选择性转发单元，LiveKit 服务端）可能下发 VP8 / VP9 / AV1，需在订阅时约束 codec。
  • 格式：H264 的 SPS/PPS（解码参数集）、AVCC ↔ Annex-B 封装；H265 的 VPS/SPS/PPS；AV1 的 OBU。
  • 时间：RTP timestamp → PTS（显示时间戳）、关键帧标志、丢包 / 乱序。
  • E2EE：端到端加密开启时，码流在解密前是密文。
  • simulcast：SFU 可能同时下发多路不同分辨率层，切换时 SSRC 会变。

3.3 VideoDecoder 接口要点

参照 webrtc-sys/src/nvidia/h264_decoder_impl.cpp:90 的现成实现：

int32_t Decode(const webrtc::EncodedImage& input_image,
               bool missing_frames,
               int64_t render_time_ms) override;
  • 输入：EncodedImage（一帧压缩后的编码图像）—— 正是硬件解码器需要的东西，不需要方案 B 的旁路通道。
  • 需实现：Configure(const VideoDecoder::Settings&)、RegisterDecodeCompleteCallback(DecodedImageCallback*)、Release()；解码完成回调 DecodedImageCallback::Decoded(VideoFrame&)。
  • 输出：webrtc::VideoFrame + VideoFrameBuffer。仓库已有 webrtc-sys/include/livekit/dmabuf_video_frame_buffer.h，嵌入式可考虑 DMA-BUF 零拷贝，避免显存→内存拷贝。
  • 格式适配：input_image.data() 是 RTP 解包后的访问单元；H264 需补齐 SPS/PPS 并统一成硬解要求的 Annex-B（或 AVCC，取决于 VPU 驱动）。

3.4 SDP 与 codec 协商（容易漏的一步）

GetSupportedFormats()（video_decoder_factory.cpp:94-119）决定 SDP（会话描述协议，用来协商 codec）里对外声明的解码能力。video_decoder_factory.cpp:45-69 的 IsInternalH264DecoderAvailable() 是很好的先例：先实际探测解码器能否 Configure() 成功，再决定是否对外声明支持。

  1. 新工厂只声明硬解真正支持的 codec（如 H264 / H265）。
  2. 订阅时仍需在 RoomOptions / 订阅选项侧约束 codec，否则 SFU 可能选 VP8 / AV1，硬解无事可做。
  3. 注意 video_decoder_factory.cpp:146-165：H264 的 packetization-mode 严格匹配会失败，代码已做放宽重试 —— 新工厂要沿用，否则 SDP 协商对不上。

3.5 下游仍有一次拷贝

即使解码在硬件里完成，livekit-ffi/src/room_apis/server/video_stream.rs:159 的 colorcvt::to_video_buffer_info(frame.buffer, dst_type, normalize_stride) 仍会按 C++ 请求的目标格式做转换。若硬件输出本身就是 NV12 / DMA-BUF，可考虑新增一种 VideoBufferType 或走零拷贝句柄进一步省掉这次转换 —— 属于 A 的可选优化，不是必需。

3.6 验证方式

webrtc-sys/test/ 下已有 benchmark_nvidia.h、benchmark_vaapi.h、benchmark_openh264.h 等编解码基准，可照此加一个硬件解码基准，观测：CPU 占用、解码帧率、端到端延迟、丢帧率、首帧时间。

3.7 工作量与风险

  • 改动面：仅 webrtc-sys（C++）+ build.rs，不碰 FFI 协议、不碰 C++ 公开 API，向后兼容最好。
  • 风险：VPU 驱动的码流格式适配、异步解码回调与 WebRTC 线程对齐、多实例并发、Configure 失败时是否回退软解、平台条件编译。
  • 局限：拿不到码流，无法自己录制 / 转发 / 多路分发；仍受 WebRTC 解码管线与渲染时序约束。

4方案 B 深化：旁路导出未解码码流

4.1 原理：接收侧已有 FrameTransformer 通道，不必改 libwebrtc 本体

RtpReceiverInterface::SetDepacketizerToDecoderFrameTransformer 把 FrameTransformer（帧变换器，WebRTC 的可插拔钩子）插在 depacketizer（RTP 包重组回一帧）之后、解码器之前，因此能拿到未解码的编码帧。

用途源码位置
E2EE 接收侧挂解密变换器webrtc-sys/src/frame_cryptor.cpp:164
帧元数据接收侧挂 PacketTrailerHandlerwebrtc-sys/src/packet_trailer.cpp:641-648
接收侧直接读编码帧字节webrtc-sys/src/packet_trailer.cpp:303-307 — TransformReceive() 里 frame->GetData()，另有 GetSsrc() / GetTimestamp()
三个阶段定义libwebrtc/src/native/packet_trailer.rs:50-59 — WebrtcReceive（解包后编码帧）→ DecoderUpload（交给解码器）→ DecoderOutput（解码帧给 sink）
挂接入口libwebrtc/src/native/packet_trailer.rs:271-281 create_receiver_handler(...)；livekit/src/room/track/remote_video_track.rs:182-194 用 transceiver.receiver()
关键结论 照着 PacketTrailerTransformer 写一个"复制并旁路导出"的变换器即可拿到码流，不需要给 libwebrtc 打补丁。webrtc-sys/libwebrtc/patches/ 下 14 个补丁都是构建 / 兼容 / 外部音频源相关，无旁路解码相关。

4.6 六个硬约束（不粉饰）

① 单槽 + 链式，绝不能覆盖

每个 RtpReceiverInterface 只有一个 depacketizer→decoder 变换器槽，已被 E2EE 与 PacketTrailer 占用，靠 ChainedFrameTransformer（frame_cryptor.cpp:32-78,188-219）串联。接收侧顺序是 first = timestamp_transformer, second = e2ee_transformer（:204-206）——若房间开启 E2EE，只有解密之后的节点才能拿到明文码流。

② 不能吞帧

packet_trailer.cpp:378 必须执行 cb->OnTransformedFrame(std::move(frame)) 把帧交还管线，否则解码器收不到数据，渲染、统计、PLI（关键帧请求）全部异常。Tap 只能旁路复制。这意味着 libwebrtc 仍会跑一次解码，白耗 CPU —— 除非配合方案 A 换成硬解，或注册 no-op decoder。

③ 拿到的是"访问单元"，不是现成裸流

codec需要处理的格式问题
H264SPS/PPS 补齐、AVCC ↔ Annex-B 转换、IDR 判定
H265VPS/SPS/PPS、Annex-B
VP8 / VP9帧头 / uncompressed header、关键帧标志
AV1OBU 边界；packet_trailer.cpp:308 已用 av1::IsAv1Frame() 特判

发送侧 livekit-capture/src/encoded/h26x.rs 有 H26x 处理可借鉴，但接收侧没有现成转换代码。

④ 时间、丢包与 simulcast

需要 RTP timestamp → PTS、关键帧标志、帧序号。packet_trailer.cpp:321-337 专门处理了 simulcast（同时下发多路不同分辨率层）切换导致的 SSRC 变化并清理旧条目 —— 说明这些坑真实存在，Tap 实现要照此处理，否则层切换后时间戳会碰撞。

⑤ 线程与背压

当前仓库 AGENTS.md：FFI 回调线程（Rust Tokio 线程）禁止阻塞；每订阅 reader 线程上限 20。Tap 回调里只能做一次内存拷贝 + 入有界队列，绝不能等 VPU、写文件或同步解码；队列满时要有明确丢帧策略（参考 libwebrtc/src/native/video_stream.rs:147-301 的 VideoFrameQueue，已实现 latest / bounded / unbounded 三种策略）。

⑥ codec 协商

嵌入式硬解多只支持 H264/H265，需在订阅选项侧约束，否则拿到硬解不了的码流。

4.7 验收建议

  • P0：日志确认每帧 GetData().size() > 0、RTP timestamp 单调递增、关键帧间隔合理；E2EE 开 / 关两种情况都测。
  • P1：压测队列不阻塞 FFI 线程（观察回调延迟 P99）；simulcast 层切换时无崩溃 / 无时间戳回退。
  • P2：端到端把码流喂给硬件解码器，比对解码帧率、花屏率、与 WebRTC 自身解码的画面一致性。

4.8 工作量与风险

  • 改动面：4 层、约 10+ 文件，含 proto 与 C++ 公开 API 扩展。
  • 风险：破坏 E2EE / 帧元数据链、吞帧导致解码异常、码流格式适配、线程阻塞、协议兼容性、fork 升级冲突。
  • 维护：全部落在 client-sdk-rust 子模块；rust-release-check.yml 要求 pin 对应已发布 release，改动后即私有 fork，后续要反复合并。

5.2 决策树

5.3 针对"嵌入式硬件解码"的推荐

  1. 首选 A：目标只是省 CPU、画面照常渲染时，A 的收益 / 风险比最好，且不动 FFI 协议与 C++ 公开 API，与当前仓库 AGENTS.md 的约束最契合。缺口很明确 —— 没有 Rockchip / V4L2 / MPP 的 VideoDecoder，照 nvidia/h264_decoder_impl.cpp 补一个即可。
  2. 先验证再扩展：无论选哪条，都先做"最小可验证"步骤（A：解码器能 Configure + 吃 EncodedImage；B：Transform 里能打印 GetData().size()），再谈协议与 API。
  3. 必须 B 时：严格按 P0 → P1 → P2，先把 ChainedFrameTransformer 顺序和"不吞帧"两件事做对，再往外扩。
  4. 结合当前工程状态：cpp-tools/ 未初始化、尚未构建，任何改动前先补齐工具链并跑一次基线构建；涉及 client-sdk-rust 的架构改动，按 AGENTS.md 要求先与开发者确认，并评估 rust-release-check.yml 带来的 fork 维护成本。

8.3 GitHub arm64 公共 runner 的编译原理

GitHub 官方文档（当前）：公共仓库的标准托管运行器免费且不限量；ubuntu-22.04-arm / ubuntu-24.04-arm 为 4 vCPU / 16 GB / arm64。本仓库 CI 已在使用（builds.yml:35-36,39-40、make-release.yml:32-37、tests.yml:153-161）。

方式CPU 指令头文件 / 库Rust 参数
x64 上编 arm64（交叉 / 模拟）需 QEMU 模拟或交叉工具链需目标板 sysroot要 --target aarch64-unknown-linux-gnu
arm64 runner 原生编译VM 本身 aarch64，直接跑系统自带 aarch64 glibc / 头文件不加 --target

源码依据：CMakeLists.txt:264-272 的 RUST_TARGET_TRIPLE 只在 macOS 设置了 CMAKE_OSX_ARCHITECTURES 时赋值，Linux 为空；cmake/run_cargo.cmake:35-38 只有该值非空才追加 --target，Linux 不加 → cargo 用 host triple。

代价：产物绑定 glibc 基线 编译期链接的就是这台 VM 的系统库 —— Ubuntu 22.04 glibc 2.35（24.04 为 2.39）、系统 libstdc++、libcurl.so.4（docs/building.md:368-370）。官方按 OS 版本分别打包（make-release.yml:309）正是为此。这与第 5.3 / 6 章的嵌入式 sysroot 陷阱一致：CI 产物是"Ubuntu arm64 服务器能用的库"，不是任意 arm64 Linux 都能用。
